# USB protocol v1

UTF-8/ASCIIの改行区切りJSON。1要求は改行を除いて最大768バイト、1応答は改行を含め最大1023バイト。
CRLFも受理します（CRも受信バッファ768バイトの計数に含む）。空行は無視し、過大行は次の改行まで捨てます。未定義のキー・操作は拒否します。
PCは同一接続で一度に1要求を送る運用を基本とし、要求IDは0～4294967295の整数を使います。

```json
{"id":1,"op":"start"}
{"id":2,"op":"status"}
{"id":3,"op":"info"}
{"id":4,"op":"pd"}
{"id":5,"op":"isdu_read","index":16,"subindex":0}
{"id":6,"op":"isdu_write","index":24,"subindex":0,"data":"74657374"}
{"id":7,"op":"stop"}
{"id":8,"op":"events"}
```

| 操作 | 動作 |
| --- | --- |
| start | 接続処理を開始。既に動作中ならリセットせず成功。応答時点で接続完了とは限らない |
| stop | ポート停止。進行中ISDUは終了エラーになる |
| status | state、busy、protocol=1、cycle_us、異常カウンター、イベント件数、ISDU期限など |
| info | Page 1から取得したVendorID、DeviceID、Revision、PD長、最小周期、ISDU能力 |
| pd | 最新の有効な入力データとsample_time_100us。未接続・PD無効時はエラー |
| isdu_read | Index=0～65535、Subindex=0～255。完了時に同じIDで1応答 |
| isdu_write | 上記にdataを追加。1～232バイトの偶数桁16進文字列。完了時に1応答 |
| events | 収集済み診断イベントを古い順に最大6件取り出す。remainingとdroppedも返す |

ISDUは非同期に実行し、周期通信と同じM-sequenceで転送します。2件目のISDUはbusyで拒否します。
ISDU中でもstatus等は別IDで受け付けるため、複数要求を使う実装ではIDで応答を照合してください。
通常のPythonクライアントは1件ずつ送信します。

```json
{"id":5,"ok":true,"data":"53454e534f52"}
{"id":5,"ok":false,"error":"isdu_failed","code":-4,"device_error":32785}
```

device_errorは16bitのサービスErrorTypeを保持します。例えば32785は0x8011です。
ローカルなサービス待ち時間切れは0x1100、不正ISDU形式は0x5700として返す場合があります。
code=-100はbusy、-101は未接続、-102はISDU非対応、-103は通信喪失、-104は全体時間切れです。
起動時のlast_error=-20は初版未対応の能力、-21は表現できる周期を超える条件です。
ISDUの応答準備待ちは標準設定5秒です。要求全体の上限は最低30秒とし、通信周期・OD幅・
最大PDUの分割数・2回の再送・応答準備待ち・診断読出し1回分・実装の余裕から延長します。
現在のリンクでの全体上限は`status.isdu_timeout_us`（µs）で取得できます。
132.8ms周期・OD 1バイトでは約112.85秒です。全体上限到達時は-104を返してポートを停止します。
この予算は無制限の診断イベントや任意のタスク遅延を保証するものではありません。

**PC側の期限も合わせて設定してください。** 別リポジトリのPythonクライアントの既定35秒では、
長周期と長い応答準備待ちの組合せを待ち切れないことがあります。接続確立後の`status`から
`isdu_timeout_us`を取得し、PCの要求期限をその値にUSB通信の余裕を足した時間へ設定します。
このファームウェア変更だけでは既存PCクライアントの期限は自動更新されません。

## 診断イベント

通信タスクはセンサーのイベントフラグを検出すると、診断メモリーを読み、イベントを保存してから
StatusCodeを書いて確認します。周期入力の受信とISDU通信も継続します。
詳細付きイベントと、旧形式StatusCodeからの標準イベント変換を扱います。

`status`には`event_pending`、`events_available`、`events_dropped`、`last_event_error`を追加しています。
`event_pending`はセンサー側の確認待ち、`events_available`はPCがまだ取り出していない件数です。
確認応答を失ってリンクを再確立しても、読み終えたイベントは保存します。
`last_event_error=-103`は、診断の読出し／確認中にリンクを失ったことを示します。

```json
{"id":8,"ok":true,"events":[{"sequence":1,"time_100us":12345,"qualifier":244,"type":3,"code":30480}],"remaining":0,"dropped":0}
```

`type`は0=不明、1=通知、2=警告、3=異常です。`qualifier`は生のEventQualifierで、
発生／消失などのMODEはbits 6～7にあります。`time_100us`は読出し完了時のMCU時刻です。
連番`sequence`と時刻は32bitで周回します。

キューは16件で、満杯時は最古のイベントを破棄し、累計`events_dropped`／`dropped`を増やします。
`events`で取り出したイベントはキューから除かれます。返信を受信できなかった場合の再取得は保証しません。
キューはUSB切断・stop・リンク再確立では保持し、MCUの再起動で消えます。
USBへの自発的なメッセージは追加していません。PCは`status`／`events`を要求して取得します。
既存の要求IDに対応する返信形式は維持します。

`status.link_quality_percent`は通信カウンターからの概算品質です。比率の乗算と加算は64bitで計算します。

MCUのsample_time_100usは起動後の100µsカウンターで、32bit周回します。PCの絶対時刻ではありません。
周期は機器の最小周期・通信フレーム長・実装の余裕を満たす表現可能値に切り上げ、下限は2msとします。
最短周期性能を保証する実装ではありません。

## 切断とバックプレッシャー

USBの送受信キューは固定長です。PCの受信が止まってもIO-LinkタスクはUSB書込みを待ちません。
最新の入力PDのみを保存し、全サンプルの記録は保証しません。
検出したUSBバスリセット・切断では部分行と旧セッションのキューを破棄します。
既に受け付けたISDUは完了する場合があります。再接続しても書込みを自動再送しません。
HWCDCで検出できない単なるPCアプリの終了では、セッション境界が通知されない場合があります。
Pythonは接続ごとにランダムな開始IDを選び、古いIDの応答を無視します。
応答不明の書込みは読出し確認してから再試行してください。
